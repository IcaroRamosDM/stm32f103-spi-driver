# Project Architecture

## Overview

This project implements a reusable SPI communication stack for STM32F103C8T6 using libopencm3.

The implementation is divided into independent layers to separate:

- hardware access
- protocol abstraction
- peripheral-specific logic
- application behavior

The final example uses a MAX7219 LED matrix driver as a real SPI peripheral validation.

This architecture allows the generic SPI driver to be reused for other peripherals such as:

- LoRa transceivers
- external flash memories
- sensors
- DAC/ADC devices
- display controllers

without modifying the BSP layer.

---

## Layered Structure

```text
main
↓
app
↓
MAX7219 driver
↓
generic SPI bus driver
↓
BSP SPI
↓
STM32 hardware
```

Each layer has a single responsibility.

---

## Layer Responsibilities

---

### `main.c`

Responsible for:

- system initialization
- startup sequencing
- infinite application loop

It does not contain business logic.

Example:

```c
clock_setup();
gpio_setup();
spi_bus_init();
max7219_init();

while (1)
{
    app_spi_demo_run();
}
```

This keeps the firmware entry point minimal and predictable.

---

### `app/`

Responsible for:

- demonstration logic
- validation sequences
- visible matrix patterns
- test orchestration

Examples:

- corner validation
- pixel walk
- smile pattern
- checkerboard pattern

The application layer uses the public driver API only.

It does not access hardware registers directly.

---

### `drivers/max7219/`

Responsible for:

- MAX7219 register control
- matrix abstraction
- framebuffer management
- logical coordinate mapping
- rotation and mirror handling

Public API examples:

```c
max7219_init();
max7219_clear();
max7219_set_pixel();
max7219_draw_pattern();
```

This layer converts logical coordinates into physical module coordinates.

This avoids coupling application code to module-specific assembly variations.

---

### `drivers/spi/`

Responsible for:

- generic SPI transactions
- register writes
- buffer writes
- reusable peripheral communication API

Public API examples:

```c
spi_bus_write_register();
spi_bus_write_buffer();
```

This layer does not know which peripheral is connected.

It only provides SPI transport.

---

### `bsp/`

Responsible for:

- RCC clock enable
- GPIO configuration
- SPI peripheral configuration
- chip select control
- SysTick timing
- onboard LED control

Examples:

```c
spi_setup();
spi_transfer_byte();
spi_cs_select();
```

This is the only layer that directly touches MCU hardware configuration.

---

## Why Separate BSP and Driver

A common bad practice is coupling protocol logic directly inside peripheral setup code.

Example of poor design:

```c
spi_setup();
send_max7219_command();
```

inside the same module.

This project separates:

```text
hardware configuration
≠
device protocol
```

This improves:

- reuse
- testing
- readability
- maintenance

The same SPI bus layer can later be reused by a LoRa SX127x driver without changing the BSP, for instance.

---

## Startup File

This project uses a manually maintained startup file:

```text
startup/startup_stm32f103c8.s
```

instead of autogenerated startup code.

This provides:

- explicit vector table control
- predictable reset flow
- easier interrupt debugging
- full ownership of initialization

The project intentionally avoids code generation tools.

---

## Orientation Mapping Problem

MAX7219 matrix modules are not physically standardized.

Different vendors mount the LED matrix with different physical rotations.

This creates a mismatch between:

```text
logical coordinates
```

and

```text
physical LED position
```

Example:

```c
max7219_set_pixel(1, 1, 1);
```

should represent:

```text
top-left corner
```

but may not, depending on module assembly.

The driver solves this using:

```c
MAX7219_MATRIX_ORIENTATION
MAX7219_MIRROR_X
MAX7219_MIRROR_Y
```

This guarantees a consistent public API independent of module layout.

---

## Framebuffer Strategy

MAX7219 does not provide practical state readback for matrix control.

Because of this, the driver maintains an internal framebuffer:

```c
static uint8_t max7219_framebuffer[8];
```

This allows:

```c
max7219_set_pixel()
```

to update individual pixels safely without losing existing row state.

Without a framebuffer, partial updates would be unreliable.

---

## Validation Strategy

The project was validated in progressive stages:

1. SPI bring-up
2. register write verification
3. MAX7219 initialization
4. all LEDs on/off
5. checkerboard pattern
6. corner mapping validation
7. pixel walk animation
8. orientation verification
9. mirror verification

This reduced debugging complexity and isolated failures early.

---

## Design Goal

The objective is not only to drive a LED matrix.

The real goal is to provide:

```text
a reusable and maintainable SPI driver architecture
```

that can serve as the base for future peripherals and more complex projects.
