# SPI Communication Flow

## Overview

This project uses SPI1 from STM32F103C8T6 to communicate with a MAX7219 LED matrix driver.

Communication follows the standard SPI master-slave model:

```text
STM32 → Master
MAX7219 → Slave
```

The MCU controls:

- clock generation
- chip select
- data transmission timing

The MAX7219 only responds when selected.

---

## Physical Signals

The project uses:

| STM32 Pin | SPI Role | MAX7219 Pin |
|---|---|---|
| PA5 | SCK | CLK |
| PA7 | MOSI | DIN |
| PA4 | CS | CS / LOAD |
| GND | GND | GND |
| VCC | Power | VCC |

`DOUT` from MAX7219 is not used in this project.

It is only required for daisy-chain configurations with multiple modules.

---

## Signal Meaning

---

### SCK

```text
Serial Clock
```

Generated by the master.

It defines when bits are sampled.

Without clock, no SPI communication exists.

---

### MOSI

```text
Master Out Slave In
```

Data sent from STM32 to MAX7219.

For this project:

```text
STM32 → MAX7219
```

The MAX7219 receives all commands through this line.

---

### MISO

```text
Master In Slave Out
```

Data returned by the slave.

MAX7219 does not require meaningful readback for normal operation, so MISO is not used.

This is why the module exposes:

```text
DIN
```

and

```text
DOUT
```

instead of standard MOSI/MISO labels.

---

### CS

```text
Chip Select
```

Also called:

```text
LOAD
```

on MAX7219 modules.

This signal defines when the slave should accept incoming data.

Important rule:

```text
CS LOW  → device selected
CS HIGH → device idle
```

The MAX7219 latches received data when CS returns HIGH.

This is critical.

---

## Why CS is Manual

Some SPI peripherals allow automatic NSS handling.

This project intentionally uses:

```text
manual CS control
```

through:

```c
spi_cs_select();
spi_cs_deselect();
```

Reasons:

- explicit transaction boundaries
- predictable timing
- easier debugging
- reusable behavior for future peripherals

This is especially important for devices like:

- MAX7219
- LoRa SX127x
- SPI Flash

where command framing matters.

## SPI Configuration

Implemented in:

```text
src/bsp/spi.c
```

---

## GPIO Configuration

### SCK + MOSI

Configured as:

```c
GPIO_CNF_OUTPUT_ALTFN_PUSHPULL
```

because these pins are controlled by the SPI peripheral hardware.

This is called:

```text
alternate function mode
```

The firmware does not manually toggle these pins.

The SPI peripheral drives them directly.

---

### CS

Configured as:

```c
GPIO_CNF_OUTPUT_PUSHPULL
```

because CS is manually controlled by software.

This allows:

```c
gpio_clear();
gpio_set();
```

for explicit transaction control.

---

## SPI Mode

Configured using:

```c
SPI_CR1_CPOL_CLK_TO_0_WHEN_IDLE
SPI_CR1_CPHA_CLK_TRANSITION_1
```

This produces:

```text
SPI Mode 0
```

Meaning:

- clock idle state = LOW
- data sampled on first clock edge

MAX7219 expects this mode.

Using incorrect CPOL/CPHA usually causes silent communication failure.

---

## Baudrate

Configured as:

```c
SPI_CR1_BAUDRATE_FPCLK_DIV_16
```

Example:

```text
72 MHz / 16 = 4.5 MHz
```

This is intentionally conservative for reliable bring-up.

Higher speeds can be used later if required.

Initial validation should prioritize stability.

---

## Data Format

Configured as:

```c
SPI_CR1_DFF_8BIT
SPI_CR1_MSBFIRST
```

Meaning:

- 8-bit transfers
- Most Significant Bit first

MAX7219 expects register + value pairs using 8-bit frames.

---

## NSS and Software Slave Management

The STM32 SPI peripheral still internally expects NSS handling even when using manual CS.

This is solved using:

```c
spi_enable_software_slave_management();
spi_set_nss_high();
```

This prevents the SPI peripheral from entering invalid states.

Without this, the MCU may incorrectly behave as a slave or block transfers.

This is often misunderstood during early SPI development.

---

## SPI is Full-Duplex

Even when only transmitting:

```c
spi_send(...)
```

the hardware also receives one byte.

This is how SPI works physically.

For every transmitted byte:

```text
1 byte TX
+
1 byte RX
```

always occur together.

Because of this:

```c
spi_transfer_byte()
```

returns the received byte.

Even though MAX7219 does not use useful RX data, other peripherals will.

This makes the API reusable.

---

## Transaction Example

Sending:

```c
max7219_write_register(0x0A, 0x08);
```

means:

```text
register = intensity
value    = medium brightness
```

Execution:

```text
CS LOW
send 0x0A
send 0x08
CS HIGH
```

When CS rises, the MAX7219 applies the new value.

This exact timing matters.

---

## Why `spi_transfer_byte()` Exists

Instead of writing:

```c
spi_send();
spi_read();
```

everywhere, the project centralizes this in:

```c
spi_transfer_byte()
```

Benefits:

- cleaner code
- reusable abstraction
- easier future changes
- simpler debugging

This is a small function with high architectural value.

---

## Validation Strategy

SPI was validated progressively:

1. LED blinking with SPI initialized
2. raw byte transfer test
3. register write
4. MAX7219 initialization
5. visible matrix patterns

This avoids debugging protocol issues and hardware issues at the same time.

Validation order matters significantly in embedded systems.
