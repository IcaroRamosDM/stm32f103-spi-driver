# MAX7219 Driver

## Overview

This project uses the MAX7219 as a real SPI peripheral to validate the generic SPI communication layer.

The MAX7219 controls:

- 8x8 LED matrix modules
- 7-segment display modules

through a simple register-based SPI protocol.

In this project, it is used with a single 8x8 LED matrix.

The objective is not only visual output.

The MAX7219 is used to validate:

- SPI register writes
- chip select timing
- reusable driver architecture
- logical coordinate mapping
- framebuffer strategy

---

## Communication Model

The MAX7219 always receives:

```text
1 byte → register address
+
1 byte → register value
```

Example:

```c
max7219_write_register(0x0A, 0x08);
```

means:

```text
Intensity register = medium brightness
```

Every command is a register write.

There is no high-level protocol.

Only address + value.

---

## Important Registers

| Register | Address | Purpose |
|---|---|---|
| DECODE_MODE | 0x09 | 7-segment decoding |
| INTENSITY | 0x0A | LED brightness |
| SCAN_LIMIT | 0x0B | active digits |
| SHUTDOWN | 0x0C | normal operation |
| DISPLAY_TEST | 0x0F | full display test |
| DIGIT0 → DIGIT7 | 0x01 → 0x08 | matrix rows |

For matrix modules:

```text
DECODE_MODE = disabled
```

because raw bit control is required.

---

## Initialization Sequence

Implemented in:

```text
max7219_init()
```

Sequence:

1. Disable display test
2. Disable decode mode
3. Enable all rows
4. Configure brightness
5. Enable normal operation
6. Clear display

This ensures deterministic startup behavior.

Without proper initialization, the display may appear unstable or partially inactive.

---

## Matrix Model

Each register:

```text
DIGIT0 → DIGIT7
```

represents one matrix row.

Each bit inside the value controls one LED.

Example:

```text
0xFF → entire row ON
0x00 → entire row OFF
0x81 → border LEDs ON
0x18 → center LEDs ON
```

This allows direct bit-level control.

---

## Public API

Examples:

```c
max7219_clear();
max7219_all_on();
max7219_checkerboard();
max7219_set_pixel();
max7219_draw_pattern();
```

The application layer only uses these functions.

It never writes raw registers directly.

This keeps peripheral-specific logic isolated.

---

## Why a Framebuffer is Required

The MAX7219 does not provide practical matrix state readback for normal control.

This creates a problem:

```c
max7219_set_pixel(row, column, enabled);
```

must update only one LED while preserving all others.

Without stored state:

```text
existing row information would be lost
```

because writing a row replaces the entire register value.

To solve this, the driver maintains:

```c
static uint8_t max7219_framebuffer[8];
```

Each entry stores one logical row state.

This allows safe partial updates.

This is required for reliable pixel-level control.

---

## Logical Coordinates

The driver API uses:

```text
row = vertical axis
column = horizontal axis
```

Meaning:

```text
(1,1) = top-left
(1,8) = top-right
(8,1) = bottom-left
(8,8) = bottom-right
```

This is the public contract of the driver.

Application code should never depend on module-specific physical assembly.

---

## Orientation Problem

Many MAX7219 modules are assembled differently by different vendors.

This means:

```c
max7219_set_pixel(1,1,1);
```

may not physically light the top-left LED.

The module may be:

- rotated
- mirrored
- mounted with swapped axes

This is a hardware variation problem, not a SPI problem.

---

## Driver Solution

The driver provides:

```c
MAX7219_MATRIX_ORIENTATION
MAX7219_MIRROR_X
MAX7219_MIRROR_Y
```

This allows logical coordinates to remain stable regardless of module assembly.

Supported rotations:

```text
0°
90°
180°
270°
```

Optional mirroring:

```text
horizontal
vertical
```

This makes the public API hardware-independent.

---

## Corner Validation Strategy

The most reliable validation was:

```c
max7219_set_pixel(1,1,1);
max7219_set_pixel(1,8,1);
max7219_set_pixel(8,1,1);
max7219_set_pixel(8,8,1);
```

This validates:

- axis direction
- orientation correctness
- mirror correctness

This is significantly more reliable than testing only symmetric patterns like:

```text
smile
checkerboard
```

because symmetric patterns may hide mapping errors.

The project uses this as the primary orientation validation method.

---

## Pixel Walk Validation

After corner validation:

```c
app_spi_demo_pixel_walk();
```

was used to validate traversal direction.

Expected behavior:

```text
left → right
top → bottom
```

This confirms:

- logical coordinate consistency
- predictable animation behavior

This is useful for future scrolling animations.

---

## Design Goal

The objective is not only to blink LEDs.

The real goal is:

```text
reliable matrix abstraction
```

that hides:

- physical module layout
- register details
- SPI transaction details

from the application layer.

This makes future animations and reusable projects significantly easier.
